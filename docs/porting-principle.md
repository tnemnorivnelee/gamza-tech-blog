# 이식 원칙

1차(이식) 단계 동안만 적용하는 규칙이다. 1차 동안에는 모든 작업 전에 읽는다. 결정 기록은 `backend-plan.md` 1절에 있다.

1차가 끝나면 이 파일을 지우고, 이 파일을 가리키는 곳(`AGENTS.md`의 이식 원칙 섹션과 핵심 원칙 1단계의 괄호, 구조 목록의 항목, `README.md`의 안내)도 함께 정리한다. 가리키는 곳은 `grep -rn porting-principle`로 찾는다.

1차는 옛 백엔드의 동작을 그대로 옮긴다.

- 옮기기 전에 옛 저장소(`potato-club/GamzaTechBlog-back`, 브랜치 `master`)에서 동작을 확인한다. 운영 중이던 서버가 `master`와 다를 수 있으므로, API 계약의 최종 기준은 프론트 저장소의 생성된 클라이언트(`src/generated/api`)이다.
- 옛 서비스에 없던 기능, 보안 강화, 사용성 개선, 동작 변경을 넣지 않는다(예: 다중 기기 로그인, 요청 횟수 제한, 보안 헤더, 헬스체크). 옛 동작을 읽다가 개선할 점이 보이면 `docs/improvement-candidates.md`에 기록하고, 구현은 옛 동작대로 한다. 비즈니스 로직은 옛 백엔드를 최대한 따르고, 후보를 비교해 새로 정하지 않는다.
- 읽는 코드가 없는 설정은 동작이 아니다. 이식하지 않는다.
- 보안상 그대로 이식할 수 없는 동작(예: GitHub 토큰을 평문으로 저장)은 먼저 묻는다.
- 구현 방식(라이브러리, 파일 구조, 이름)은 눈에 보이는 동작이 같으면 자유롭다.
