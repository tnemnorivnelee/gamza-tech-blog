# 개선 후보

작성일 2026-11-05 · 상태: 계속 추가

1차(이식) 동안은 비즈니스 로직을 옛 백엔드처럼 구현한다(사용자 지침, 2026-11-05). 옛 동작을 읽다가 고치는 편이 좋겠다고 판단한 것은 여기에 적고, **구현은 하지 않는다.** 이식이 끝나면(`porting-principle.md`가 사라질 때) 이 문서를 보고 하나씩 논의한다.

`backend-plan.md` 12절의 "제안했다가 뺀 것"(여러 기기 동시 로그인, 리프레시 토큰 형식 변경, 요청 횟수 제한, 보안 헤더, 이미지 파일 시그니처 검사, 헬스체크, GitHub 스코프 축소)도 같은 후보다. 거기에 이미 있으므로 옮겨 적지 않는다.

항목마다 옛 동작(출처), 1차에서 하는 일, 개선안을 한 줄씩 적는다. 새 항목은 아래에 번호를 이어 붙인다.

## 인증 (M2에서 찾은 것)

### 1. role이 안 맞을 때의 문구가 "인증에 실패했습니다."
- 옛 동작: 로그인했지만 role이 안 맞는 사용자에게 403 · `J005` · "인증에 실패했습니다."를 `ResponseDto` 모양으로 줬다고 추정한다 [미검증]. (`m2-auth-plan.md` 5절, D1)
- 1차: 같은 모양으로 구현한다.
- 개선안: 403 · `C006` · "접근이 거부되었습니다."

### 2. 만료된 액세스 토큰이 HTTP 400으로 나간다
- 옛 동작: 서명 오류, 만료, 형식 오류가 모두 400 · `C005` "유효하지 않은 타입 값입니다."로 나간다. (`m2-auth-plan.md` 3.2)
- 1차: 그대로 구현한다.
- 개선안: 만료와 서명 오류를 구분하는 JWT 코드(`J001` 등)로 나눈다.

### 3. 인증 실패 응답에 `code` 필드가 없다
- 옛 동작: 인증 실패는 코드를 `data`에 담는다. 프론트의 `actionResult.ts`는 `body.code`를 읽으므로 이 경우 상태 기반 기본값(`UNKNOWN_ERROR`)이 된다. (`m2-auth-plan.md` 3.2)
- 1차: 그대로 구현한다.
- 개선안: 인증 실패도 일반 에러 모양(`ErrorResponse`)으로 통일한다.

### 4. 액세스 토큰과 리프레시 토큰이 구별되지 않는다
- 옛 동작: 같은 서명과 같은 클레임으로 만들어서, 리프레시 토큰을 액세스 토큰 자리에 써도 통과한다. (`m2-auth-plan.md` 5절)
- 1차: 그대로 구현한다.
- 개선안: 토큰 종류 클레임을 넣고 검사한다.

### 5. reissue가 리프레시 쿠키를 다시 내려주지 않는다
- 옛 동작: Redis의 만료만 30일로 늘린다. 브라우저의 리프레시 쿠키 수명은 로그인 때 정해진 30일 그대로다. (`m2-auth-plan.md` 3.3)
- 1차: 그대로 구현한다.
- 개선안: 쿠키도 다시 내려서 "연장"이 실제로 맞게 한다.

### 6. 쿠키로만 인증한 요청은 로그아웃해도 블랙리스트에 오르지 않는다
- 옛 동작: 블랙리스트에 올리는 액세스 토큰을 헤더에서만 읽는다. 프론트는 항상 헤더를 같이 보내서 실제로는 문제가 없다. (`m2-auth-plan.md` 3.4)
- 1차: 그대로 구현한다.
- 개선안: 인증에 쓴 토큰을 그대로 블랙리스트에 올린다.

### 7. `PRE_REGISTER`·`PENDING` 사용자는 로그아웃을 부를 수 없다
- 옛 동작: 로그아웃이 `USER`·`ADMIN`만 허용한다. 프론트는 서버 응답과 상관없이 쿠키를 지워서 화면에서는 드러나지 않는다. (`m2-auth-plan.md` 3.4)
- 1차: 그대로 구현한다.
- 개선안: 로그인한 모든 role에 허용한다.

### 8. 토큰 검증이 `sub`(발급처 표시)를 확인하지 않는다
- 옛 동작: 서명과 만료만 확인한다. `sub`는 모든 토큰에 같은 고정 문자열 `GamjaTech`라서 확인해도 지금은 보호가 늘지 않는다. (`m2-auth-plan.md` 3.1)
- 1차: 확인하지 않는다. 시험으로 고정했다.
- 개선안: 같은 키로 용도가 다른 토큰이 생기면, 4번(토큰 종류 구분)과 함께 `sub` 확인을 넣는 것을 논의한다.

### 9. 로그아웃한 액세스 토큰이 "만료된 JWT 토큰입니다."(J001)로 나간다
- 옛 동작: 블랙리스트에 있는 토큰을 `EXPIRED_JWT`(403, `J001`)로 거부한다. 실제로 만료된 토큰은 400 `C005`로 나가서(2번), 두 코드의 뜻이 서로 바뀐 모양이다. (`JwtTokenValidator`)
- 1차: 그대로 구현한다. 시험으로 고정했다.
- 개선안: 로그아웃한 토큰 전용 코드를 두고, 2번과 함께 정리한다.

### 10. `Bearer ` 접두어가 없는 헤더는 "토큰 없음"(J004)이 된다
- 옛 동작: `ACCESS`·`Authorization` 헤더 값이 `Bearer `로 시작하지 않으면 오류 없이 무시하고 다음 후보를 본다. 그래서 `ACCESS: <토큰>`만 보내면 "JWT 토큰을 찾을 수 없습니다."(403, `J004`)가 나가 원인을 알기 어렵다. 쿠키 값은 접두어 없이 그대로 읽어서 헤더와 규칙이 다르다. (`JwtProvider.resolveToken`)
- 1차: 그대로 구현한다. 시험으로 고정했다.
- 개선안: 접두어가 틀린 경우를 별도 메시지로 알리거나, 접두어 유무와 상관없이 읽는다.

### 11. 로그아웃의 헤더 읽기가 가드와 다르고, 헤더 토큰이 나쁘면 500이 된다
- 옛 동작: 로그아웃은 블랙리스트에 올릴 토큰을 `ACCESS ?? Authorization`로 한 값만 골라 `Bearer ` 검사를 한다. 가드는 `ACCESS`에 접두어가 없으면 `Authorization`으로 넘어가 인증하지만, 로그아웃은 `null`이 되어 아무것도 올리지 않는다. 또 남은 수명을 계산하다 헤더 토큰이 만료·위조면 예외가 나 500 `C004`가 된다. 그 앞에서 리프레시 토큰은 이미 지워졌고 쿠키 만료는 나가지 않아 반쯤만 로그아웃된다. (`JwtProvider.resolveAccessTokenFromHeader`, `BlacklistServiceImpl`)
- 1차: 그대로 구현한다. 시험으로 고정했다.
- 개선안: 가드가 인증에 쓴 토큰을 그대로 블랙리스트에 올리고(6번과 함께), 리프레시 토큰 삭제·블랙리스트·쿠키 만료를 한 덩어리로 처리해 중간에 실패해도 반쯤 로그아웃되지 않게 한다.

### 12. reissue 뒤에는 로그아웃해도 리프레시 토큰이 남을 수 있다
- 옛 동작: reissue는 `refresh:<토큰>` 키의 만료만 늘리고 `userRefresh:<githubId>` 키는 로그인 때 만료 그대로 둔다. 로그인 30일 뒤에 `userRefresh` 키가 사라지면 늘어난 `refresh` 키는 살아 있는데, 로그아웃은 `userRefresh` 키로 토큰을 찾으므로 `refresh` 키를 지우지 못한다. 쿠키는 만료시키지만, 이미 복사해 둔 리프레시 토큰으로는 reissue가 계속 된다. (`RefreshTokenDao.touchTtl`)
- 1차: 그대로 구현한다. 시험으로 고정했다.
- 개선안: reissue에서 두 키의 만료를 함께 늘리거나, 로그아웃이 요청 쿠키의 리프레시 토큰도 함께 지운다.

### 13. 남은 수명이 0초인 액세스 토큰을 로그아웃하면 500이 된다
- 옛 동작: 로그아웃은 액세스 토큰의 남은 수명(초, 내림)을 그대로 Redis `SET … EX`에 넘긴다. 만료까지 1초 미만 남은 토큰은 0이 되고, Redis는 `EX 0`을 거부해서 예외가 나 500 `C004`가 된다. 그 앞에서 리프레시 토큰은 이미 지워졌고 쿠키 만료는 나가지 않아 반쯤만 로그아웃된다(11번과 같은 모양). 옛 `getRemainingAccessTokenValidity`는 `(만료 시각 - 현재) / 1000`을 정수로 내린 뒤 `max(…, 0)`으로 음수만 막아서 0은 그대로 나간다. (`JwtProvider`, `BlacklistServiceImpl`) 옛 서버에서 실제로 500이 나는지는 **[추정]**이다.
- 1차: 그대로 옮긴다. `RedisTokenStore`는 남은 수명을 그대로 넘기고, 진짜 Redis 시험이 0이면 던지는 것을 고정했다. 시험에 끼우는 가짜(`InMemoryTokenStore`)는 이때 던지지 않는다.
- 개선안: 남은 수명이 0 이하이면 블랙리스트에 올리지 않는다(어차피 곧 만료되어 가드가 거부한다). 11번의 "한 덩어리 처리"와 함께 고친다.

### 14. Lua 교체가 실패하면 한 덩어리가 아닌 대체 경로로 조용히 넘어간다
- 옛 동작: 로그인의 리프레시 토큰 교체는 Lua로 한 덩어리 처리를 먼저 시도하고, 예외가 나면 경고만 남기고 키를 하나씩 바꾸는 `rotateRefreshTokenLegacy`로 돌아간다. 이 경로는 명령 네 개가 따로 가서 같은 사용자가 동시에 로그인하면 토큰이 둘 남을 수 있고, Lua 쪽의 수명 최소 1초 보정도 없다. Lua가 계속 실패해도 서비스는 겉으로 정상이라 문제가 숨는다. (`RefreshTokenDao`)
- 1차: 그대로 옮겼다(사용자 결정). 진짜 Redis 시험이 대체 경로가 Lua와 같은 결과를 만드는 것과 경고를 남기는 것, 대체 경로까지 실패하면 던지는 것을 고정한다.
- 개선안: 대체 경로를 없애고 Lua 실패를 그대로 던지거나, 대체 경로를 쓸 때 경보를 보낸다.

## GitHub 로그인 (M3에서 찾은 것)

### 15. 로그인이 실패하면 오류 화면 없이 로그인이 처음부터 다시 시작된다
- 옛 동작: `SecurityConfig`에 실패 처리기가 없다. Spring 기본 실패 주소가 `loginPage + "?error"`, 즉 시작 경로 `/oauth2/authorization/github?error`로 보이고, 이 주소가 다시 GitHub 승인 화면으로 이어진다. 사용자가 승인을 취소하거나 `state`가 맞지 않아도 같다. 설정 오류(예: 틀린 client secret)가 계속되면 이동이 반복되어 브라우저가 "리다이렉트가 너무 많다"며 멈출 수 있다. 기본 실패 주소는 코드로 확인한 것이 아니라 **[추정]**이다. (`m3-github-login-plan.md` 3.7)
- 1차: D2에서 정한 방식으로 구현한다.
- 개선안: 실패를 프론트의 오류 안내 화면으로 보내고, 원인(취소, `state` 불일치, GitHub 오류)을 구분해서 로그를 남긴다.

### 16. 로그인 뒤 처리(이메일·프로필 이미지·GitHub 토큰 저장)가 실패해도 아무도 모른다
- 옛 동작: 응답을 보낸 뒤 비동기로 돌고, 실패는 로그만 남긴다. 토큰 저장이 실패한 사용자는 로그인은 되지만, 나중에 게시글을 GitHub에 동기화할 때 `GITHUB_OAUTH_TOKEN_NOT_FOUND`로 처음 실패를 알게 된다. 이메일을 채우지 못해도 프론트 가입 화면(`signup/page.tsx`)이 `email`을 요청에 담아 보내므로 사용자가 직접 입력할 수 있는 것으로 보인다 **[추정]**. (`GithubPostLoginHandler`, `GithubTokenValidator`)
- 1차: D6·D7에서 정한 범위만큼 옛 방식대로 옮긴다.
- 개선안: 토큰 저장을 로그인 응답 전에 하거나, 실패하면 다시 시도하고 사용자에게 재로그인을 안내한다.

### 17. `state`를 서버 메모리 세션에 두어서 재시작에 약하고 인증 전 요청이 서버 메모리를 쓴다
- 옛 동작: Spring의 기본 동작으로 `state`(위조 방지 값)를 서버 메모리의 세션에 넣고 브라우저에는 세션 쿠키만 준다. `SecurityConfig`에 보관 방식 설정이 없어서 프레임워크 기본값을 쓴 것으로 보인다 **[추정]**. 서버를 재시작하거나 배포하면 로그인 도중이던 사용자는 `state`를 잃어 실패하고(15번처럼 로그인이 다시 시작된다), 서버를 여러 대로 늘리면 요청이 다른 서버로 가서 실패한다. 로그인 시작 경로는 로그인 전에도 열려 있어서 호출할 때마다 세션이 하나 생긴다. (`m3-github-login-plan.md` D1)
- 1차: 옛 방식대로 `express-session`의 `MemoryStore`에 둔다(사용자 결정). 콜백이 끝나면 세션을 지운다.
- 개선안: `state`를 `HttpOnly; Secure; SameSite=Lax` 쿠키에 담고 콜백에서 비교한 뒤 지운다. 서버가 기억할 것이 없고 새 패키지도 없다. 비교는 `timingSafeEqual`로 한다. 세션이 다른 곳에도 필요해지면 보관소를 ioredis로 직접 만든 Redis 보관소로 바꾼다(`connect-redis`는 ioredis와 맞지 않는다).

### 18. 로그인 뒤 이동 주소의 `location`이 쓸모없을 수 있고 로컬 프론트로 돌아올 수 없다
- 옛 동작: `location`을 **콜백 요청**에서 읽는다. 콜백 주소는 GitHub가 정하므로 시작 요청에 붙인 `?location=`은 전달되지 않는다. GitHub 앱의 콜백 주소 등록값에 `location`이 들어 있지 않았다면 항상 비어 있고 기본값(`app`)으로만 이동했을 것이다 **[추정]**. 이동 주소가 `https://{location}.{접미사}`라서 포트와 `http`를 쓸 수 없고, 로컬 프론트(`localhost:3000`)로는 돌아올 수 없다. (`OAuth2LoginSuccessHandler`, `m3-github-login-plan.md` D3)
- 1차: 옛 형식 그대로 옮긴다. 허용 목록 검사는 시험으로 고정한다.
- 개선안: 프론트 주소 하나를 환경변수(`FRONTEND_URL`)로 받고 `location`을 없앤다. 여러 곳으로 보내야 하면 시작 요청의 값을 세션에 실어 나른다(세션에는 이미 `state`가 있다). 허용 목록 검사는 그대로 둔다.

## 데이터 계층 (M4에서 찾은 것)

### 19. 날짜가 시간대 정보 없는 `DATETIME`으로, 서버 시간대에 기대어 저장된다
- 옛 동작: `BaseTime`이 `LocalDateTime`에 `@CreatedDate`를 쓰고, 컬럼은 시간대 정보가 없는 `datetime(6)`이다. `application.yml`·`Dockerfile`에 시간대 설정이 없어서 값은 서버 프로세스의 기본 시간대로 찍힌다 **[확인함]**. 덤프의 글 작성 시각 분포로 보면 KST 벽시계 값이다 **[추정]**. 서버를 다른 시간대의 컨테이너로 옮기면 새 행만 9시간 어긋난다. (`m4-prisma-plan.md` 4절·D7)
- 1차: 옛 행과 어긋나지 않게 같은 기준(KST 벽시계)으로 쓰고 읽는다.
- 개선안: UTC로 저장하고 응답에 오프셋(`+09:00` 또는 `Z`)을 붙인다. 기존 행은 한 번 변환해야 하고, 프론트의 날짜 표시도 함께 확인해야 한다.

### 20. Prisma 8이 정식으로 나오면 올릴지 검토한다
- 현재: npm의 `latest`가 `8.0.0-rc.33`(릴리스 후보)이고 안정 버전은 7.10.1이다. 8은 설정·스키마·런타임 구조가 7과 다르다. (`m4-prisma-plan.md` 5절·D1)
- 1차: 7.10.1로 고정한다.
- 개선안: 8의 정식판이 나오고 문서가 안정되면 올릴 만한지 본다. 7의 스키마를 읽는 호환 경로가 있다고 문서에 나오지만 확인하지 않았다 **[미검증]**.

### 21. 안 쓰는 합격 조회 테이블에 이름·전화번호 숫자가 평문으로 있다
- 옛 동작: `admission_results`에 `name`, `phone_digits` 컬럼이 있고 7행이 들어 있다 **[확인함]**. 이 API는 프론트가 쓰지 않아 1차 범위 밖이다. (`m4-prisma-plan.md` 4절 5번)
- 1차: 테이블과 데이터를 그대로 둔다(스키마에서 지우지 않는다).
- 개선안: 쓰지 않는 기능이면 이 테이블의 데이터를 삭제하거나 보관 기간을 정한다. 쓴다면 전화번호는 해시로 저장하고 조회는 해시 비교로 바꾼다.

## 읽기 API (M5에서 찾은 것)

### 22. 검색어가 비었거나 없으면 400이 아니라 500이다
- 옛 동작: `GET /api/v1/posts/search`는 `keyword`가 비면(`@NotBlank` 위반) 또는 없으면(필수 파라미터 누락) 옛 예외 처리기가 따로 다루지 않는 예외라서 500 `C004`가 된다 **[확인함: 코드, 운영 응답은 미관찰]**. (`PostController`, `GlobalExceptionHandler`, `m5-read-api-plan.md` 3.1)
- 1차: 옛 동작대로 500 `C004`를 낸다. 시험으로 고정한다.
- 개선안: 입력이 틀린 요청이므로 400 `C001`로 응답한다.

### 23. 좋아요 목록에서 태그가 없는 글의 `tags`가 `[null]`이다
- 옛 동작: `LikeQueryAdapter`가 글과 태그를 왼쪽 조인해서 태그 이름 목록을 만들 때 null을 걸러내지 않는다. 태그가 없는 글(현재 데이터에서 3개)을 좋아요 했다면 응답이 `"tags":[null]`이다. 글 목록은 같은 경우 `[]`이다. **[확인함: 코드]**
- 1차: 옛 동작대로 `[null]`을 낸다.
- 개선안: null을 걸러서 `[]`로 낸다. 프론트가 `tags`를 문자열 배열로 가정하면 오류가 날 수 있는 모양이다.

### 24. 정렬 파라미터를 받는 목록이 요청의 `sort`를 무시하거나 반영하는 곳이 섞여 있다
- 옛 동작: 글 목록·태그별·검색·내 글·공개 프로필의 글·좋아요 목록은 쿼리에 `createdAt` 내림차순이 박혀 있어서 요청의 `sort`를 무시한다. 소개 목록과 내 댓글 목록은 `sort`를 반영하고, 없는 속성이면 500이 된다. 명세에는 모두 `sort` 파라미터가 있다. **[확인함: 코드]**
- 1차: 옛 동작대로 옮긴다(`m5-read-api-plan.md` 3.1).
- 개선안: 쓰는 곳이 정렬을 못 바꾼다면 명세에서 `sort`를 빼고, 지원하는 정렬은 허용 목록으로 검사해서 틀리면 400으로 응답한다.

### 25. 읽기 캐시가 시간 만료에 기대고, 인기 글은 최근 7일 글만 대상이다
- 옛 동작: 글 쓰기가 일부 캐시만 지운다. 홈 피드와 공개 프로필 캐시는 무효화가 없어서 최대 5분 낡은 값이 나간다(예: 글을 올린 뒤 홈 피드에 5분 동안 안 보일 수 있다). 인기 글은 작성한 지 1주 안의 글에서 좋아요 상위 3개라서, 최근 글이 없으면 빈 목록이다(복원한 데이터는 마지막 글이 2026-05-16이라 지금은 비어 있다). **[확인함: 코드]**
- 1차: 옛 동작대로 옮긴다(캐시는 M5-5, 무효화는 쓰기와 함께 M6).
- 개선안: 쓰기 때 홈 피드·공개 프로필도 무효화하거나 만료를 짧게 한다. 인기 글은 기간 안에 글이 없으면 기간을 넓힌다.

### 26. 글 상세(공개)에는 댓글이 들어 있는데 댓글 목록 API는 로그인이 필요하다
- 옛 동작: `getPostDetail`은 로그인 없이 호출되고 응답에 그 글의 모든 댓글(작성자 닉네임, 프로필 이미지 주소 포함)이 들어 있다. 같은 내용을 주는 `getComments`는 로그인을 요구한다. 접근 규칙이 서로 맞지 않는다. **[확인함: 코드와 접근 규칙 표]**
- 1차: 옛 동작대로 옮긴다.
- 개선안: 댓글을 공개로 둘지 로그인 사용자에게만 보일지 정하고 두 API를 같은 규칙으로 맞춘다.

### 27. 이미지 주소를 절대 URL로 DB와 글 본문에 박아 둔다
- 옛 동작: 이미지를 올리면 `https://<버킷>.s3.<리전>.amazonaws.com/<키>` 전체를 DB 컬럼과 글 본문(마크다운)에 저장한다. 저장소를 옮기면 DB 세 컬럼과 본문의 주소를 모두 바꿔야 한다(글 본문 56개, 이미지 주소 151개). **[확인함: 코드와 복원 DB]** (`m5-read-api-plan.md` 10절)
- 1차: 옛 방식 그대로 전체 주소를 저장한다. 저장소를 옮길 때는 앞부분만 치환한다.
- 개선안: 키(`post-images/<uuid>_name.png`)만 저장하고 앞부분은 설정(`IMAGE_PUBLIC_BASE_URL` 등)에서 붙인다. 응답을 만들 때 합치면 저장소를 옮겨도 DB를 건드리지 않는다.

### 28. 범위를 넘긴 쪽의 `totalElements`와 `totalPages`가 0이다
- 옛 동작: 글 목록 계열(`fetchPosts`)은 요청한 쪽에 글이 없으면 개수를 세지 않고 0을 돌려준다. 글이 58개인데 `page=99`를 부르면 `totalElements: 0`, `totalPages: 0`이다. 마지막 쪽을 넘어서면 전체 개수가 사라지는 모양이다. **[확인함: 코드, 시험으로 고정]** (`PostQueryAdapter`, `m5-read-api-plan.md` 3.2)
- 1차: 옛 동작대로 0을 낸다.
- 개선안: 쪽이 비어도 실제 `count`를 돌려준다. 프론트가 "마지막 쪽 번호"를 `totalPages`로 계산하면 범위를 넘긴 요청에서도 일관된다.

### 29. 검색 명세는 `pageable` 객체 하나인데 서버는 평평한 쿼리만 읽는다
- 옛 동작: 명세(OpenAPI)에서 `searchPosts`의 쿼리가 `keyword`와 `pageable`(객체)이라서 생성 클라이언트가 `pageable[page]=0`처럼 중첩해서 보내고, Spring은 이를 읽지 못해 기본값을 쓴다. 프론트가 이를 알고 `postService.server.ts`에서 평평한 쿼리(`page`, `size`, `sort`)를 직접 만들어 부른다. **[확인함: 코드]** (`m5-read-api-plan.md` 3.1)
- 1차: 명세는 옛 모양 그대로 두고, 서버는 평평한 쿼리를 읽으며 중첩 형식은 무시한다(기본값). 시험으로 고정한다.
- 개선안: 명세를 `page`, `size`, `sort` 세 파라미터로 고치고 프론트의 우회 코드를 없앤다. 프론트 저장소 변경이라 별도 이슈가 필요하다.
